# Subsystems

Every runtime module on `main`, by layer: what it does, where it lives, which exported data it runs, and what is
still missing. The header comment at the top of each file is the detailed reference; `notes/PLAYTHROUGH.md` has the
system-by-system status, and `notes/TECH_DEBT.md` has every difference from DSR (look rows up with
`grep -n '^| <id>' notes/TECH_DEBT.md`).

Paths are relative to `ps2/proto/src` unless they start with `tools/` or `ps2/`.

## Platform and core

**GS state** (`gs.c`, `gs.h`, `gs_budget.h`). Owns every GS register word, the display set-up, and VRAM accounting
per owner. See [architecture.md](architecture.md#gs-state-and-vram).

**Memory** (`mem.c`, `mem.h`). Static, boot-temp, frame, pool, page and scratchpad regions; the boot / load / play
state machine and the malloc-in-play counters. See [architecture.md](architecture.md#memory-regions).

**Runtime switches** (`cvar.c`, `cvar.h`). Fallback switches a test script can flip at boot.

**Measurement** (`hitch.c`, `prof.c`, `lpass.c`, `aligncheck.c`). `hitch.c` wraps the heap calls and prints the
periodic `hitch:`, `spike:` and `alloc:` lines. `prof.c` is the `PROFILE` build's per-pass EE cycle and cache-miss
counters (cache misses read 0 in PCSX2). `lpass.c` breaks the logic pass down by part (player, AI, ESD, events...).
`HEAPMAP` builds log the live heap by caller for `tools/heapmap.py`.

**Maths** (`vmath.c`, `vmath.h`): vectors, matrices, quaternions on the EE's FPU.

## IO

**Packs** (`pack.c`, `pack.h`). Every runtime file is an entry in an LZ4 pack (64 KB blocks) read from `host:` (PCSX2
HostFs) or `cdrom0:` (the ISO). Reads go to the IOP as requests while the EE decompresses the previous batch. Async
reads (`pack_read_async`) feed the streamer.

**IOP module** (`ps2/proto/iop/dsrsnd/`, protocol in `dsrsnd_rpc.h`). One module holds the sound server (SPU2
voices, disc streams) and the disc server the packs read through. Splitting the two is step 4.5.

## Graphics

**Order table** (`ot.c`, `ot.h`) and **2D writer** (`g2d.c`, `g2d.h`): see
[architecture.md](architecture.md#the-order-table).

**VU1 renderer** (`vu1.c`, `vu1.h`, `vu1_layout.h`, `vu1*.vsm`). Programs generated by `tools/vu1/gen.py`:
`vu1map2` (map list batches), `vu1mapi` (indexed map batches), `vu1clip` (map triangles that cross the guard band),
`vu1skin2` / `vu1skinclip` (skinned characters, bone palette windows of up to 61 bones), `vu1fx` (particles).
Map batches are prebuilt VIF packets from the exporter, sent by reference. The skin programs take a palette of bone
matrices per window, so any skeleton size draws (`MDL_MAX_BONES`).

**Textures** (`texcache.c`). The map's textures live in a VRAM pool (LRU) filled by uploads inside the map chain
(PATH2) right before the first batch that needs them. Two mip levels from the exporter. CLUTs stay resident. Menus
and the loading screen borrow the top of the pool (`tc_pin`).

**Relief** (`bump.c`). DSR's normal maps baked to a per-pixel light ratio at export and applied as a second pass over
the bumped map chunks (`BUMP_BAKED`).

**Camera and projection** (`render.c`, `camera.c`, `camera_i.h`). The camera the simulation reads (enemy omission,
NPC visibility) is in `camera.c`; `render.c` holds the projection, near plane (0.5 m) and the EE-path triangles.
Field of view from `LockCamParam` row 0.

**Post** (`main.c`): two depth ranges split at 50 m, and the far depth-of-field bands drawn with the flip as a
deferred order-table entry. Fog per area comes from the area's FogBank row, applied in the VU1 programs.

Missing (phase 2): a material table from MTD files, prebuilt character packets, specular and environment passes on
every material, character point lights, shadows, water, FFX models and weapon trails, a third mip level, VRAM
enforcement.

## World

**World blocks** (`world.c`, `world.h`). The game world is a set of blocks: each one an exported part of an MSB map
with its own pack (`tools/area.py` BLOCKS, the block table in `world.pak` from `tools/export_world.py`). Blocks turn
on and off in the background by the player's position and time-to-reach (`WORLD_REACH`), so walking between areas
needs no loading screen. A block that is on holds its "lite" set (collision index, map tables, events, draw groups);
its visual cells stream separately. When a block turns on, `world.c` turns on its enemies, events, objects and
effects. Warps and deaths settle the world behind the loading screen (`world_settled`).

**Map drawing** (`map.c`, `mapblock.c`, `map.h`, `map_i.h`). Draws every on block's map: sky, panorama, horizon,
coarse and near levels per cell, each level drawn where the finer one is missing or out of range. Draw-group and PVS
filters choose the chunks; the frustum test runs per chunk. The player's point light is added on the map around
them (`MAP_PLIGHT`).

**Streamer** (`mapstream.c`, `mapstream_i.h`, `msarena.c`, `residency.h`). A residency plan ranks every streamable
item (coarse cells, near parts, backdrops, textures, collision tiles) into classes by distance and visibility, cuts the
plan to fit the arena, then reads the missing items highest class first, nearest first, merging neighbours into one
request. The arena is 10,752 KB of 64 KB pages; budgets per block are solved at export so what a spot needs fits
(`tools/world_budget.py` fails the build otherwise).

**Visibility** (`pvs.c`, `drawgrp.c`). PVS from `tools/pvs_bake.c`: one row of visible units per 8 m camera cell.
DSR's draw groups: a map chunk draws only while the collision part under the player shares a draw group with it.

**Collision** (`collision.c`, `coltile.c`). DSR's Havok collision meshes exported as triangles with hit-filter masks:
floor height, capsule push-out with wall sliding, rays for the camera. Each block's collision is paged in 16 m tiles
that stream with the player (`COL_TILES`).

**Navmesh** (`nav.c`). DSR's MSB navmesh parts near a block's enemies: A* over the triangles, then the funnel through
shared edges.

Planned (phase 4): split these files into lifecycle, planner, page arena, level drawing and visibility; one level
chain with resident parents; streaming sources with velocity (player, warp target, respawn point); DSR's read
priority classes; 32 KB disc alignment; a whole-game manifest.

## Scene

**Models** (`model.c`, `model.h`). Skinned models from `model.bin` (player: `tools/export_model.py`; enemies and
objects: `tools/export_chr.py`), drawn any number of times with their own pose. Animations are Havok tracks resampled
at export, with root motion.

**Ragdolls** (`ragdoll.c`). DSR's ragdoll bodies from the chr hkx: capsules per main bone with joint limits, used as
hit bodies while alive and simulated (position-based dynamics) once the character dies.

Planned (phase 5): one animation hierarchy and pose pool for player, enemies, NPCs and animated objects, with update
rate by distance.

## Game

**Player** (`player.c`, `player.h`, `player_data.h`). The player runs DSR's own `c0000` ESD (`esd.c`): pad input
becomes ESD requests, TAE windows from the playing animation set the action flags (cancels, invincibility, turning,
stamina regeneration rate), root motion and gravity move the character proxy over the collision. Stamina, turn speed
and dash values come from params and the exe. All player data loads from `player.gd` at boot.

**Enemies** (`enemy.c`, `enemy.h`, `omit.c`, `npc.c`). Each MSB enemy part with an exported character pack is
placed when its block is on. An enemy runs the shared `enemyCommon` ESD and DSR's Lua AI (`ai.c`), moves by root
motion over the collision and navmesh, and attacks with TAE windows. Placement by distance, an active cap, a pose
pool, and DSR's update omission levels (characters that matter less this frame update every few frames). Human NPCs
(`c0000` placements) are stand-ins drawn with the player's model.

**Lua AI** (`lua0.c`, `lua0.h`, `ai.c`, `ai.h`). `lua0` is a small Lua 5.0 VM running DSR's compiled AI scripts
(`aiCommon` plus each map's script) as re-serialized by `tools/lua50.py --pack`: every 5.0 opcode DSR's AI uses,
tables, closures, interned strings, light userdata with method tables, and a mark-and-sweep collector that runs
between calls under a time budget. `ai.c` is the engine side of DSR's goal system: logic functions per
`NpcThinkParam`, Lua goals (`Activate` / `Update` / `Terminate` / `Interupt`), and the goals DSR implements natively
(Wait, MoveToSomewhere, Guard, KeepDist, ApproachStep, CommonAttack and others) in C. DSR's sight cones and hearing
are ported (`AI_PERCEPT`). All AI runs on the interpreter; a build-time translation of the Lua to C was trialled and
dropped (see [data-pipeline.md](data-pipeline.md#how-each-kind-of-dsr-data-reaches-the-game)).

**ESD runtime** (`esd.c`, `esd.h`, `esd_env_move.c`). Runs a character's EzState state machine as the exe does: each
group steps once a frame, first true condition wins, transitions run exit, pass and entry commands, while-commands run
every frame, expressions are the ESD's own stack bytecode. Environment queries and commands dispatch first to the
shared movement and combat handlers, then to the player's or enemy's own hooks. Unknown queries return 0 and unknown
commands do nothing; function ids are named in `data/esd_names.json`.

**Event scripts** (`event.c`, `event.h`, `ev_chr.c`, `ev_obj.c`, `ev_misc.c`). DSR's EMEVD as compact bytecode: event
instances with their own arguments, condition groups evaluated every frame, skips, waits, restarts, the event's own
flag when it ends. Wired to flags, MSB regions and entities, enemies, collision parts, object colliders (fog walls,
gates), ObjActs (chests, levers), treasures, warps, the boss bar and sound. Every unsupported instruction is kept by
the exporter as a logged stub, never dropped. One `events.bin` per block and `evcommon.bin` once.

**Combat** (`combat.c`, `combat.h`, `combat_data.h`). Hurtboxes for every character, attack capsule sweeps from
weapon and body dummy polys during TAE attack windows, the physical damage formula with AtkParam and correction
graphs, guard, poise and super armour, hit reactions and knockback, throws (`ThrowParam`), lock-on. Values from
`combat.gd`.

**Character stats** (`chrstat.c`, `chrstat.h`). Max HP and stamina, equip load, defence per damage type, poise and the
attack rating of each hand, from the saved stats and equipment with the exe's formulas, kept as a resident snapshot.

**Status effects** (`status.c`, `status.h`). Poison, toxic, bleed and curse: buildup meters filled by hits that carry
a status SpEffect (`SpEffectParam` buildup fields), resistances from `chrstat.c`, the effect once a meter fills. A
general SpEffect system (rings, buffs, every effect type) is step 5.8.

**Items, flags, progress, save** (`items.c`, `flags.c`, `progress.c`, `save.c`). DSR's item database from the item
params (names, icons and descriptions only while a menu is open). Event flags in DSR's own id layout, stored as pages
per area and section. Progression (souls, humanity, stats, equipment, inventory, Estus, last bonfire) from
`progress.gd` for a new game. Saves hold progression plus flag pages in two alternating slots with a CRC, on the
memory card or `host:`.

**World objects** (`objects.c`, `physics.c`, `pickup.c`, `bonfire.c`). Breakables with pre-fractured pieces simulated
by a small rigid-body solver until they settle. Animated objects (doors, levers, gates, chests) playing their Havok
animations with their boxes pushing the player. Treasure shines, the pickup animation and DSR's item-get dialog,
enemy drops from `ItemLotParam`. Bonfires: lighting, resting (HP, Estus and enemy reset), the rest menu, the death
loop and bloodstains.

**Game data loader** (`gamedata.c`, `gamedata.h`). Loads `player.gd`, `combat.gd` and `progress.gd` from `c0000.pak`,
checks each layout id against the generated header and relocates its pointers. See
[data-pipeline.md](data-pipeline.md#generated-headers-and-game-data-records).

Planned (phases 5 and 6): handles instead of pointers; player and enemies as one character type in parts (model,
animation, control, action, brain, stats, hit); one TAE runner with upper and lower body layers; full damage types,
scaling and defences; SpEffects; bullets and magic; part-assembled NPCs with talk ESD, shops and level-up; bosses.

## Front end

**HUD and menus** (`hud.c`, `menu.c`, `drb.c`, `loading.c`). DSR's HUD (bars, quick slots, souls, humanity, YOU
DIED) and Start menu screens (Equipment, Inventory, Status, System) from the game's own `menu.drb` layouts, sprites
and fonts. DSR's loading screen with its item hints. All drawn through the UI stream of the 2D writer.

**Sound** (`sound.c`, `sound.h`). DSR's FMOD banks re-encoded as SPU2 ADPCM: resident sound effects on 42 voices with
3D volume and pan, music and ambience streamed from disc on three stereo slots. Played by TAE sound events, MSB sound
emitters, EMEVD and area ambience. 8 kHz today, no reverb or voices yet.

**Effects** (`fx.c`, `fx.h`). DSR's FFX particle systems and effect lights of an area: emitters near the eye emit,
particles are built on the EE in the emit phase and drawn on VU1 (`vu1fx`) after the opaque passes. Effect lights
(bonfires) add to the character light.

Planned (phase 7): a screen stack with input focus, title, character creation, level-up, shop and warp screens,
higher sample rates, reverb, voices, cutscenes and movies, background saves.

## Test drivers

**Test runner** (`testscript.c`, `testscript.h`). Plain-text scripts loaded at boot drive the pad, camera, spawns,
waits, flags, cvars, screenshots and checks without a rebuild. See [build-and-test.md](build-and-test.md).

**Debug overlay** (`debug_hud.c`): fps, VU1 chains, collision, loads, world blocks, enemies, objects, events,
effects and memory region high-water marks (`option hud`), plus the debug-only world drawing.

**The Lab** (`ps2/proto/lab/`): the simulate phase as a host program. See
[build-and-test.md](build-and-test.md#the-lab).
